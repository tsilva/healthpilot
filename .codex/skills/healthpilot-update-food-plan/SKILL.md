# Update food plan

Update the person's existing plan, not an unrelated ideal diet. A call to this skill authorizes the selected profile's context and food-plan updates and local PDF publication. Follow explicit standing email authorization in the selected profile's personal context without asking again on each run. It does not authorize changes to clinical sources, calendar events or another profile. Work from the Healthpilot repository root and follow its `AGENTS.md`.

## Canonical deliverables

- Personal guidance: selected live YAML's `data_sources.profile_context_md_path`.
- Current editable plan: `~/.config/healthpilot/profiles/{slug}.food-plan.md`, linked by `data_sources.nutrition_md_path`.
- Latest printable plan: `.output/{slug}/daily-plan/food-plan.pdf` (absolute path in the final response). Keep the menu on page 1; add a second page of swaps when requested in personal context. Replace this stable file on successful updates; dates never enter its filename.
- Email delivery when authorized: attach the validated PDF to the fixed recipient in personal context, apply the `Food Plan` Gmail label, and explain changes against the previous plan and the data supporting them.
- Optional dated history is archival only. Keep the current Markdown coherent rather than accumulating contradictory revisions. Review timestamps and evidence-window dates support freshness; historical filenames are not required.

## Review the person and evidence

1. List live profiles with `ls ~/.config/healthpilot/profiles/*.yaml`. Use the named profile; ask which one only if ambiguous. Never fall back to repo example profiles. Parse YAML without displaying tokens or credentials. Read the **complete** personal context and current food plan; validate configured sources. If context is absent, resolve or bootstrap it from known user statements before personalizing. Bootstrap a missing plan only for the requested person.
   Before editing, save the existing canonical Markdown and rendering spec, when present, under `.output/{slug}/daily-plan/assets/{run_id}/previous/`, using a unique run ID even for same-day runs. This is the comparison baseline for this invocation; preserve it through retries. If no previous plan exists, identify this as the initial plan instead of inventing a comparison. Read standing delivery preferences from the selected context; recipient addresses belong there, outside the repository.
2. Persist new user preferences, goals and constraints in context first. Retire conflicting old guidance. Attribute reports of fatigue, hunger, bloating, intolerance or poor energy as observations; do not invent diagnoses, allergies, measured weights or confirmed causal food triggers. Keep inferred proposals separate from user instructions.
3. Read recent `health_log.md` and relevant `entries/*.processed.md`, normally the latest 4–6 weeks; inspect raw entries where wording or timing matters. Look for energy, appetite, bowel symptoms, bloating, reflux, sleep, training, medication changes and actual adherence. Inspect older entries when needed to interpret an ongoing issue. Record the actual available period, not just the requested period. Review relevant labs/exams when they could change dietary advice; clinical/parser sources remain read-only.
4. Read [Google Health retrieval documentation](../../../docs/google-health.md). Inspect `healthpilot google-health-status --profile <slug>` privately. Retrieve **freshly on every invocation**, normally 28 completed source-calendar days ending yesterday, with:
   ```bash
   healthpilot google-health --profile <slug> --metrics calories weight steps sleep --start YYYY-MM-DD --end YYYY-MM-DD
   ```
   Use the local CLI environment (`uv run --frozen healthpilot ...` if needed). Add HRV/resting heart rate only when recovery questions justify them. Start with 28 days, compare the last 7 with the full window; extend to 6–8 weeks for sparse weights or atypical weeks when useful. Respect source dates, timezone, units and coverage. Weight arrives in grams: convert explicitly to kg. Latest seven dates refresh automatically; use `--refresh` for relevant historical corrections. Query success does not prove complete device wear.
5. Separate valid completed days from missing, stale, partial or implausible observations. Do not count missing values as zero, include today's partial calorie total, or silently delete genuine high-activity days. Summarize valid-day count, mean/median expenditure, recent change, steps/activity pattern, sleep and available weight trend. Explain exclusions and whether the window represents normal life. Total calories already include basal and activity expenditure: never add them again. Never borrow another profile's cache. If unavailable, continue with available evidence, explicitly retain a provisional target and describe the gap; do not claim expenditure-based calibration or start OAuth without owner consent.
6. Read `routine_calendar` through the available Google Calendar plugin when configured, covering a representative upcoming week and relevant exceptions. Calendar blocks are intentions, not measured activity. Fit meals and preparation around commitments without editing events. If access fails, preserve known timing as provisional and disclose stale coverage; do not invent free time or resurrect retired schedule-file sources.

## Adapt the plan

- Choose calories from the active goal, representative expenditure, actual intake if known, weight trajectory, symptoms and activity. Wearable expenditure is an estimate, not measured maintenance. Compare 2–3 weeks of weight averages when available. If weights/adherence are absent, avoid a precise deficit claim. Prefer modest adjustments with a clear rationale over chasing day-to-day calorie changes; unchanged intake is a valid outcome.
- Do not automatically cut food for fatigue, low HRV or stalled weight. Consider sleep, illness, medication, training and under-fuelling; flag a material clinical concern separately rather than implying a menu fixes it. Research current authoritative guidance when introducing clinical recommendations or a new deficit/protein target. Respect condition-specific constraints.
- Preserve familiar meals, meal timing, food preferences and practical portion conventions. Inherit the profile's language. **Express portions of foods that require cooking as cooked, ready-to-eat edible weights**, including meat, fish, potatoes, rice, cooked vegetables and porridge. Specify preparation and draining where they affect the reference. Foods eaten uncooked use edible serving weights; packaged foods remain as sold, soup as prepared volume and oil in the profile's spoon measures. A later explicit profile instruction can override this convention.
- Calculate calories and protein using references that match the cooked food and preparation; never relabel raw/dry grams as cooked or apply raw nutrition per 100 g to cooked portions. When changing the weighing convention, choose practical cooked portions near the existing energy/protein intent, then recompute item, meal and daily totals. Explain any material intake change separately from the measurement change. Do not claim exact raw-to-cooked equivalence from unrelated database entries or a universal yield factor.
- For recipes whose water content varies (especially porridge), document the ingredient calculation and a defined final cooked batch weight in Markdown, then portion by final weight. Raw ingredient amounts may support the recipe calculation but must not be the serving instruction in the menu/PDF. If relying on a cooking yield, record its preparation-specific source or measured batch basis and uncertainty; do not invent a measured yield.
- Use label calories for specified products; otherwise document the reference and assumption. Household spoons/handfuls and mixed-fruit/nut estimates need a gram anchor and approximate calories. Do not imply all nuts or arbitrary container fillings are interchangeable. Check context-specific restrictions (including high-selenium Brazil nuts, when relevant) before generic mixtures. Do not invent supplement doses or assign unquantified ingredients zero calories.
- Respect lunch/dinner protein preferences and container capacity. If fit is uncertain, state that in the Markdown; grams are not millilitres. Keep soup/fruit separate where specified. Do not silently reduce vegetables/protein just to fill a box.
- Reconcile the **actual menu sum** with the intended target. If edits increase it materially, adjust suitable portions consistent with constraints or explicitly explain the unresolved difference; never label a higher summed menu as the old target. Explain changes and assumptions in the canonical Markdown, including evidence coverage, source references, review date and what would prompt the next adjustment. Keep obsolete instructions out of current sections; an optional short history can retain prior versions.

## Produce and verify the PDF

When the profile requests a swap sheet, preserve the main menu and add exactly one second page through the renderer's optional `swaps` object. Anchor exchanges to the current meal portions; label whether quantities match calories or protein, and show material differences in the other value. Use cooked preparation-specific references, practical rounding and brand/recipe assumptions. Respect meal-specific exclusions. Alternatives replace foods, do not add to the baseline total; explain how the selected swap changes the day's calories/protein. Refresh the sheet whenever its reference menu portions change.

Use the available PDF skill for its authoring marker and visual-verification requirements, and bundled workspace dependencies for ReportLab/pypdf. Read [the rendering contract](references/pdf-contract.md). The included renderer removes repeated hand-written table code; it does **not** make nutrition decisions.

1. Finish the coherent current Markdown menu and rationale. Create a local JSON rendering spec from its exact quantities and calories. Keep private specs under `.output/{slug}/daily-plan/assets/` or ignored scratch, never tracked skill assets.
2. Render to a candidate file under `.output/{slug}/daily-plan/`, not directly over the last good PDF:
   ```bash
   python .codex/skills/healthpilot-update-food-plan/scripts/render_food_plan.py --spec <local-spec.json> --output <candidate.pdf>
   ```
3. Verify item values match Markdown, meal sums and daily sum, cooked serving weights and matching nutrition references, unknown calories and preference compliance. Check that cooked foods have no raw/dry serving instructions and variable-water recipes have a defined final yield. Render the candidate with `pdftoppm` and inspect every page. Require one menu page and, only when requested, one swap page. No clipped cells, overlapping text, tiny text or unintended pages. If it will not fit, shorten wording; do not drop food or hide uncertainty.
4. After validation, atomically replace `.output/{slug}/daily-plan/food-plan.pdf` with the candidate on the same filesystem (e.g. `os.replace`). A failed render must leave the existing latest PDF intact. Optional archives must not replace the stable entry point. Record the stable absolute PDF path in the canonical food-plan Markdown for discovery.
5. Complete authorized email delivery below before returning the stable PDF path/link using the PDF skill's output citation, with a brief explanation of material changes, approximate calorie total and material unavailable evidence. The PDF itself contains food, portions, item calories, meal subtotals and total only, plus concise measurement/estimate notes. Put medical reasoning and source coverage in Markdown, not the printable menu.

## Email the plan and explain the revision

After successful PDF publication, complete the selected profile's standing email instructions on **every skill run**, including reviews that retain the menu. Use the fixed recipient recorded in personal context, not `me` or whichever account happens to be signed in. Standing authorization is sufficient; do not request repeated send approval. Without delivery authorization for the selected profile, return the local deliverables without borrowing another person's recipient or permission.

Compose in the plan's language. Every **subject must start with the exact literal prefix `[food-plan]`**, followed by a space; do not translate, capitalize, or prepend anything to this prefix. After the prefix, identify the person/date, the main change (or that portions are unchanged), and the principal evidence used. Keep it concise; for example: `[food-plan] {name}, {date}: portions unchanged; weight/activity review`. Verify this prefix before sending. The **body** must explain:

- What changed compared with the saved pre-run plan: foods, quantities, timing, calories/protein, or calculation/presentation corrections. Give before/after values for material numerical changes. Separate actual menu changes from evidence refreshes and wording clarifications; do not imply an old preference or measurement is new.
- Why each material change was made and which data support it: named source category, actual measurement/entry dates or coverage windows, relevant values/trends, and user preferences where applicable. Distinguish newly available evidence from older records rechecked this run and observed data from inference.
- What was deliberately retained and why, the resulting approximate calories/protein, and material uncertainty such as sparse weights, unmeasured intake, estimated expenditure, or unquantified ingredients. If nothing changed, say so explicitly and explain what was reviewed. For an initial plan, explain its basis without a fabricated previous version.

Send through the Gmail plugin with the validated stable PDF attached as `application/pdf`. Use a `multipart/mixed` MIME payload with the email text and the PDF's exact bytes in `base64_url_content` (base64url). Do not email filesystem links, credentials, parser metadata, full personal context, or unrelated clinical records. Save the comparison summary and a local delivery receipt under `.output/{slug}/daily-plan/assets/{run_id}/`, recording the recipient, subject, PDF hash, returned Gmail message ID, and send/label status.

Apply the exact Gmail mailbox label **`Food Plan`** to the sent message using `apply_labels_to_emails` with its returned message ID; create the label if missing. This is a mailbox label, not a Workspace classification label. If the connector's label actions fail, use the in-app Browser when the same Gmail account is accessible, verify the account and target message, then create/apply the label through the UI without archiving or resending. If the recipient is also the connected account, the labeled self-addressed message appears in that mailbox; Gmail cannot label a different recipient's mailbox through the sender's connection.

A labeling failure must not trigger another email: retry labeling the known message. After an uncertain send response, inspect sent mail/receipts before retrying; if delivery cannot be established, report it as uncertain rather than sending duplicates. If Gmail is unavailable or sending fails, retain the validated local PDF and prepared email, state the delivery failure, and do not claim delivery. A new user-invoked review still requires its own email even if its PDF hash matches the prior run. Finish with the PDF citation and confirmed recipient/label status.
